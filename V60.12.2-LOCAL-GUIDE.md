# Singh Academy V60.12.2 — local test/run guide

## What this update is

This is a focused follow-up to **V60.12.1** for the supplied 15-failure browser
log. It repairs the synthetic provider document encoding, test synchronization
around logout and payment creation, and the payment-alert locator.
It is **not** a new payment integration or a guarantee that a deployed payment
has settled. Existing production auth, learning, payment, footer and certificate
behavior is preserved. The only changes in application files are version labels.

## Install safely

Use the complete ZIP **or** the PATCH ZIP, not both.
- Complete ZIP: open `SINGH-ACADEMY-V60.12.2-COMPLETE`, containing backend,
  frontend, scripts and package.json.
- Patch ZIP: extract it, open its `SINGH-ACADEMY-V60.12.2-PATCH` folder, and copy
  the CONTENTS over your working V60.12.1 project root.
- Stop old dev servers/browser-test runs with Ctrl+C first.
- Back up the working source/database. Preserve backend/.env, frontend/.env.local
  (or your existing frontend/.env), stable AUTH_SECRET, the exact Mongo database
  name, and the tested backend/frontend package-lock.json files.
- **No migration, seed, reset, secret rotation or new npm dependency is required.**
- Node **22.x or 24.x** remains accepted. NVM is not a project requirement.

## Local connection settings

Edit only these entries; never replace an entire credentials file with them.

frontend/.env.local:
```env
NEXT_PUBLIC_API_URL=/api
API_PROXY_TARGET=http://127.0.0.1:5000
```

Existing local backend/.env:
```env

DEPLOYMENT_STAGE=development
PORT=5000
FRONTEND_URL=http://localhost:3000
FRONTEND_URLS=http://localhost:3000
PUBLIC_API_URL=/api
```

Keep your valid MongoDB, auth, SMTP and Stripe TEST / PayPal SANDBOX settings.
Do not paste secrets into chat. These development values are for localhost only,
not public Hostinger deployment.

## One complete local test command

From the project root, run:
```powershell
node -v
node -p "require('./package.json').version"
npm run verify:release
```

Version must be **60.12.2**. The existing fail-fast release runner still performs
installation, preflight, controlled tests, build/typecheck, audits, Chromium,
the full actual Next/browser suite, payment configuration and SMTP authentication.

The browser suite now declares **44 cases**: all original 41 remain, plus
UTF-8 provider-document checks for Stripe/PayPal and delayed-creation coverage.
This is the expected inventory, **not a claim that all 44 ran/passed during
packaging**. Read the QA report for executed results and blocked checks.

Do not run a second test/dev stack concurrently. The browser suite uses its
own .next-ui-tests output and fixture ports 3108/5109. Normal app ports remain
3000/5000. The fixtures never send real money or emails.

On a working V60.12.1 installation with this patch applied, a focused check of
the failed stage is also available:
```powershell
npm run test:ui
```
A focused browser pass does not replace the full release gate before deployment.

Reports:
- `qa/release-checks.json` — current release run; not_run does not mean passed.
- `frontend/qa/ui-results.json` — machine-readable browser results (new).
- `frontend/qa/ui-report` — browser HTML report.
- `frontend/test-results` — synthetic fixture screenshots/traces on failure.

If a check fails, keep the FIRST error. Do not skip the failing step or use
npm audit fix --force. Share reports/fixture traces only, not private .env,
production cookies, real account traces or customer records.

## Run the actual app after checks pass

Terminal 1, project root:
```powershell
npm run dev:backend
```

Terminal 2, same root:
```powershell
npm run dev:frontend
```

Leave both running. Open **http://localhost:3000** consistently (not 3108).

Terminal 3:
```powershell
npm run deploy:check -- --local --front http://localhost:3000 --api http://127.0.0.1:5000
```

Expected: zero failed smoke checks. Both identities should be 60.12.2:
backend `/api/health`; frontend `/api/app-build`. Frontend proxy `/api/health`
reports backend version only, not the frontend build version.

## Acceptance before deployment/handover

Use the existing browser first without deleting cookies, then a private window:
- Guest landing -> protected link -> credentials -> requested page.
- Normal sign-in -> /home; Events -> Logout -> landing.
- Back and Refresh must not restore the old account without deliberate login.
- Free course -> Start -> learning, no payment creation.
- New certificate appears through owner-scoped polling without a document reload.
- Two students never share enrollment, learning, answers, invoices or certificates.
- Actual Stripe TEST and PayPal SANDBOX: individual course AND membership.
  Confirm provider status, one local invoice/receipt, owned access/admin record.
  Test slow confirmation/Back/refresh without purchasing again automatically.
- Verify actual provider webhook delivery and actual intended email inbox.
  Synthetic browser tests and SMTP authentication alone do not prove either.

Only then update the existing Git repository and both Hostinger apps from the
same tested commit/lockfiles. Preserve email mailboxes and approved UI. Keep
public production/review security and upload policy; do not switch a public
server to development to bypass validation.
