## What the patch changes

### Free-course Start

The actual component now waits for hydration/session readiness, uses a synchronous one-flight enrollment lock, cancels/ignores stale owner/course responses, and keeps busy feedback until learning navigation. A signed-in free-course route shell is prefetched without creating enrollment/payment. Free Start performs one enrollment mutation and no payment/access request. The existing browser assertion still requires the exact learning route within its original expectation timeout.

These are concrete safeguards, not proof that the original failure was caused by a specific one of them. The user's full browser rerun is still required.

### Payment recovery

An unresolved attempt preserves only retry metadata (owner, kind, product, option, renewal, provider, request key, known order ID) in sessionStorage for the same tab. It is not evidence of payment. Unknown attempts cannot switch providers/options and get a fresh key merely because the old response timed out. Read-only recovery uses the existing key; an explicitly confirmed terminal order permits a new checkout only after the user's confirmation. The return page checks the requested order identity/status and removes only metadata belonging to that settled owner/order.

Page restoration no longer unlocks an ordinary in-flight mutation on an unrelated `pageshow`. Response generations prevent an old product/account request from navigating a newly selected product/account. Account isolation, provider HTTPS allowlisting, provider evidence and atomic server fulfillment remain enforced. The backend payment business/provider code is unchanged.

Storage can be unavailable, and sessionStorage is not shared across unrelated tabs/devices. No global exactly-once payment guarantee or automatic real refund is claimed.

### Certificate test measurement (correction of prior diagnosis)

`framenavigated` alone is not a document reload counter. In an executable Chromium diagnostic, `history.replaceState` on the already loaded document emitted an extra frame-navigation event with zero additional document requests and unchanged `performance.timeOrigin`. See `qa/v60.12/history-diagnostic.json`.

The revised test retains the existing 10-second certificate-visible assertion and now ALSO requires: exactly one main-frame document request, unchanged time origin, a retained page-only marker and the same URL. That is a stronger check of the user's actual requirement: no document reload. It does not simply accept two frame events. No production certificate polling/navigation code or certificate artwork was altered. The original user's second event was not proven to be `replaceState` because its trace was unavailable.

### Test runtime isolation

Previously the UI stack used Next dev and the ordinary `.next` output. The new stack builds actual Next once in `.next-ui-tests`, then starts it in production mode before assertions. It uses a separate TypeScript config, an ownership lock and cleanup of only its own process tree/output. Normal standalone deployment output stays unchanged; the fixture alone uses ordinary `next start` packaging. Browser stack startup allows 240 seconds for the build; per-test and expectation timeouts, retries=0, exact URL checks and logout assertions are unchanged.

Unexpected Next JSON/manifest errors are recorded and fail the browser command even if assertions pass. The runner does not suppress them. This eliminates shared dev-output/HMR as a factor in this test setup, not a proof of the exact origin of the user's JSON errors.

A new synthetic HTTP commerce fixture and **17 payment browser cases** cover both providers/course-membership/mobile-desktop, double clicks, lost create reply, refresh retention, switching lock, closed-order reset, cancellation, pending/retry confirmation, provider Back, settled return refresh and cross-student isolation. The **41 full browser cases are declared, not reported as executed here**.

## Single local acceptance gate

From the correct project root, with Node22 and preserved real local configuration/locks:

```powershell
npm run verify:release
```

This installs, validates, verifies the ordinary production build and tests, runs full audits, installs Chromium, runs all actual Next browser cases ONCE, then performs payment configuration and SMTP authentication checks. It stops at the first failure and writes `qa/release-checks.json`. Focused retry commands and the actual sandbox/deployment handover matrix are in `V60.12-LOCAL-GUIDE.md`.

Even a clean local gate is not a production-security certificate or real payment proof. Actual provider deliveries, per-user invoices/access, email inbox, device behavior and the final Hostinger environment still need acceptance before client handover.
