## Root cause confirmed from source + isolated Chromium reproduction

The old `media-images-v60-13.spec.ts` media handler returned the same 1x1 PNG for every `w` value. Production responsive markup truthfully described its candidate as 480w etc., but the test server returned only one pixel. This violates the fixture's implied bitmap-width contract.

Executed on system Chromium 144.0.7559.96, viewport width 1200 and the production COURSE_CARD_SIZES string:

| Response/descriptor | decode() | load event | naturalWidth |
|---|---|---|---:|
| Original one-pixel PNG, no srcset | resolved | load | 1 |
| Original one-pixel PNG described as 480w | resolved | load | 0 |
| New actual 480px PNG described as 480w | resolved | load | 347 |

Thus `naturalWidth=0` did not prove that this image failed decoding. It rounded to zero after responsive density correction. The uploaded text log does not include a Windows trace; the controlled Chromium reproduction plus exact original source establishes the fixture defect without claiming to have inspected the user's live media response.

The old PNG also had a bad IDAT CRC (stored efa3e0bf versus calculated efa2a75b). Chromium tolerated that checksum in the executed diagnostic. New PNGs have valid CRCs; the CRC difference is NOT falsely identified as the observed failure cause.

Technical references used:
- https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/naturalWidth — intrinsic density-corrected CSS width.
- https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode — successful decoding is a separate signal.
- https://playwright.dev/docs/api/class-route#route-fulfill — binary fixture response contract.
