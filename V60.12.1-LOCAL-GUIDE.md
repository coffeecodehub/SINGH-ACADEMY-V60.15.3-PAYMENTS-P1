# Singh Academy V60.12.1 — Local Node 24 testing without NVM

## What this fixes, and what it does not claim

The uploaded V60.12 `scripts/release-check.mjs` refused every Node major except
22 before any tests ran. Its root, frontend and backend `package.json` files also
declared `engines.node: "22.x"`. This is the blocker shown in your PowerShell log
on Node **24.18.0**. It is not evidence that MongoDB, payment verification or
application tests failed: the old gate had not run those checks yet.

This patch uses the consistent range **`22.x || 24.x`** across all three packages
and release/installation/verification tooling. Other majors and prerelease
runtime builds are not accepted. NVM is not checked or needed. Runtime-policy
acceptance is not a security certification or a substitute for executing tests.
Use maintained security patches within the chosen runtime family.

Do not change the existing Hostinger Node 22 setting simply because the local
computer has Node 24. Local and production runtime results are separate evidence.
The updated GitHub quality workflow declares both Node 22 and Node 24 jobs, with
all existing checks retained. Those jobs must actually pass; this package does
not mark GitHub/Hostinger checks as already run.

## 1. Apply ONE of the two ZIPs

Stop previous test/frontend/backend terminals with Ctrl+C, then back up your
working project. Use either:

- **Complete ZIP:** extract/open `SINGH-ACADEMY-V60.12.1-COMPLETE`, the directory
  containing `backend`, `frontend`, `scripts` and `package.json`.
- **Small PATCH ZIP:** copy the CONTENTS of its patch folder into the existing
  V60.12 project root. Do not put that patch folder under `frontend` or `backend`.

Preserve working private `backend/.env`, `frontend/.env.local`, exact MongoDB
database name, stable AUTH_SECRET, existing provider/SMTP credentials and tested
`backend/package-lock.json` / `frontend/package-lock.json`. The source ZIP has
no private credentials, node_modules or invented lockfile. `npm ci` still checks
an existing lockfile; without one installation resolves packages and creates
one. Do not delete a lockfile or force-upgrade packages just to hide a failure.

No migration, re-seed, database reset, student record edit or secret rotation is
needed for this runtime-tool patch. Application behavior, certificate assets and
payment logic remain unchanged from V60.12.

## 3. Check runtime, then run all local gates

From the correct project root in VS Code PowerShell:

```powershell
node -v
node -p "require('./package.json').version"
npm run check:runtime
```

Your existing `v24.18.0` is accepted; `v22.x` is also accepted. The source version
must be **`60.12.1`**. `check:runtime` is read-only, uses no network or credentials,
and checks all three package manifests so an incomplete patch is identified.

Then:

```powershell
npm run verify:release
```

No separate `npm run install:all` or long PowerShell block is needed first. The
gate runs the original checks in the original order, after runtime consistency:

1. Install dependencies using locks when supplied.
2. Local backend preflight.
3. `verify`: new runtime-tool unit tests, existing reliability/protected UI tests,
   backend tests, Sharp smoke, certificate sample, full TypeScript, production
   Next build, syntax/import validation and production audits.
4. Full backend/frontend audits, including development dependencies.
5. Install project Chromium.
6. Full actual Next/browser suite once (the original 41 declared cases; includes
   authentication, free Start, certificate update and synthetic payment cases).
7. Payment configuration check (does NOT create a charge).
8. SMTP connection/authentication check (does NOT prove inbox delivery).

An actual failed check stops the sequence. No runtime, browser or security test
is skipped to force a green message. Unsupported runtime/mixed packages now also
create a fresh report instead of leaving no report or a stale successful one.

```powershell
Get-Content .\qa\release-checks.json
```

The report records the actual Node version/platform, each check and `not_run` for
checks never reached. Its output is a local result on that runtime, not approval
of a different runtime or a live deployment. Stop at the first error and keep the
first failure/report. Do not run two release/browser stacks concurrently.

## 4. Start the real local app after all gates pass

Keep each server running in its own terminal, all opened at the project root.

**Terminal 1:**

```powershell
npm run dev:backend
```

**Terminal 2:**

```powershell
npm run dev:frontend
```

**Terminal 3:**

```powershell
npm run deploy:check -- --local --front http://localhost:3000 --api http://127.0.0.1:5000
```

Manual browser: **`http://localhost:3000`**, not `3108`. Browser-fixture servers
use `3108`/`5109` for automated synthetic tests only. Stay on the same frontend
hostname during manual login testing. Frontend `/api/health` reports the proxied
BACKEND version; `/api/app-build` independently reports the FRONTEND version.
Both should identify **60.12.1**.

## 5. Before client handover

Existing application acceptance requirements are not waived. Test guest landing,
protected destination/login, explicit Logout + Back/Refresh, free Start, course
progress, owner separation, live certificate status and video start behavior.
Use actual provider SANDBOX/TEST transactions for one individual course and one
membership per provider, and check invoice, receipt, student's grant, admin
record and intended email inbox. A synthetic payment test is not a provider
transaction; SMTP authentication is not inbox delivery.

On Hostinger, keep the existing **Node 22** deployment profile and real
production/review security configuration. Update the EXISTING repository/apps
from one commit after verification. Commit reviewed lockfiles, not secrets.
CI now checks both accepted majors; check its results rather than assuming its
presence means it ran. Build/install on Hostinger instead of uploading local
Windows node_modules. A successful local Node 24 run cannot prove an unexecuted
Node 22 deploy, and a health response alone cannot prove login/payment behavior.

This patch does not require a new app, new domain, DNS/mailbox changes, NVM on the
client's machine, disabled auditing, development mode on a public backend or
removing production upload-scanning rules. No live deployment is performed here.
