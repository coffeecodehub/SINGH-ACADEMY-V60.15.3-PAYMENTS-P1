# Singh Academy V60.8 — local test first

This is the complete application source based on V60.7. The requested changes are durable explicit logout, free-course Start actions, compact tablet navigation and the reference-based certificate master. The rest of the approved public design is retained. Read `QA-V60.8.md` for exactly what was and was not run.

## 1. Open the correct folder in VS Code

Extract the ZIP once and open its project folder. At the same level you must see `package.json`, `backend`, `frontend`, and `scripts`. Do not put this whole folder inside another repository's `frontend` or `backend`.

Keep a backup of the existing project and the actual Atlas database. Preserve your working private `backend/.env`, `frontend/.env.local`, stable `AUTH_SECRET`, `MFA_ENCRYPTION_KEY`, database name, provider/SMTP credentials, and tested `package-lock.json` files. Dependency requirements are unchanged. Never commit private .env files. Do not seed/reset an existing database to fix a loading error.

Use Node **22.x**. Check in the VS Code terminal:

```powershell
node -v
```

## 2. Local environment — no Hostinger URL in the local API target

Edit only these connection/environment values in your existing local files. Do not replace the rest of your credentials with example text.

`frontend/.env.local`:


Keep your already working MongoDB URI, authentication/MFA keys, sandbox payment and SMTP settings. If a shell environment variable overrides either file, remove that conflicting local shell value and restart the terminals. These development values are not the public Hostinger profile.

## 3. Install and verify

From the project root, run these individually; stop at an error:

```powershell
npm run install:all
npm --prefix backend run preflight
npm run verify
npm run payments:check
npm --prefix backend run mail:verify
```

`verify` includes frontend API/session tests, UI preservation checks, backend tests, image/PDF smoke tests, TypeScript checking, a real Next build and production dependency audits. Do not skip/remove tests or use `npm audit fix --force` to make it green. Existing lockfiles use `npm ci`; missing lockfiles are generated by install on your network.

There is **no V60.8 database migration**. If you have not yet run the V60.7 notification migration on this exact database, back it up and run once:

```powershell
npm run migrate:v60.7
```

This does not reset learning/payment/certificate data. V60.8 logout uses the existing session `revokedAt` field.

Stop any old V60.7/V60.6 frontend/backend terminals with **Ctrl+C** first. Start both new terminals in the V60.8 folder. If port 5000/3000 is already in use, do not silently continue against an old process; stop that old local app and re-check the health version.

## 5. Required manual acceptance

### Logout (use the existing browser too, not only an empty incognito window)

1. Sign in normally as Student A. Visit Team, a course and My Billing.
2. Click Logout. You should reach the login page and no longer see Student A in the header.
3. Use Back, Refresh and reopen the frontend. Student A must NOT return without submitting credentials.
4. While logged out, opening the frontend `/api/auth/session` directly should return `user: null`. This directly tests server logout, independently of the browser's logout marker.
5. Explicitly sign in again: normal access should return. Do not logout; reload and navigate: an otherwise valid session remains signed in.
6. Repeat with two tabs. Logout in one tab must remove student identity from the other. A separate Client Admin session is not the student's session and should not be globally cleared.
7. Simulate a brief offline/503 session check WITHOUT clicking Logout. It must show a reconnect state rather than inventing a logout. A failed explicit logout stays locally signed out but displays the need to retry SERVER revocation; do not report revocation as successful during an outage.

### Free vs paid courses

Publish a course with `accessType=free` using the existing course editor. View Course -> **Start Course** must enroll the signed-in student and open learning without checkout/provider requests. Guests are asked to sign in first. Paid courses and active membership still follow the existing entitlement and verified-payment rules.

Use Student B in a separate browser profile. Both students may enroll in the same free course, but answers, progress, attempts, billing and certificates must remain separate.

### Tablet navigation

Check 768, 1024, 1228 and 1366 CSS-pixel widths, in portrait/landscape. The existing compact navigation now covers 901–1399px too. Open/close it, choose My Billing, press Escape and click outside. Header/account controls must remain visible without overlap. The original <=900px mobile styling and >=1400px desktop styling were not redesigned.

### Certificates

The actual renderer samples are in `qa/v60.8/certificates/`. These are visibly marked SAMPLE; they are not issued qualifications.

All newly approved completions use the same cream/gold reference-based artwork, embossed seal and blue signature. Learner name, full course title, completion/issue dates, serial and verification URL come from the approval record, not from the reference screenshot. Longer real names/titles fit or wrap into the reserved field; oversized/unsupported text fails validation rather than silently corrupting the account name.

**Already-issued PDFs are stored immutable documents and will NOT silently change.** Test a newly completed/pending short course and approve it. Do not delete issued certificate records just to see the new style. Repeated Issue requests preserve the existing certificate/serial.

The central watermark was reconstructed to remove the reference's baked-in sample text. The outer artwork, paper, gold seal and blue signature are reference-derived. Dynamic field typography/line breaks necessarily depend on the actual student/course; use the included actual PDF preview to review the result, not an AI concept image.

### Payment, invoice and email regression

Existing V60.7 payment confirmation, invoice ownership and email outbox are retained. Test Stripe and PayPal SANDBOX individually and membership using only provider-approved test accounts/details. Check My Billing, Client Admin records, access dates and the paying student's inbox. Never fulfill access just because a return URL says success. Local config/SMTP authentication tests do not prove deployed webhooks or inbox delivery.
