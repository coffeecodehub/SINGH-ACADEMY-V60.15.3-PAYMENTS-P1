# Singh Academy V60.11 — Local validation and update guide

## Read before replacing files

This package patches V60.10. It is NOT a declaration that the public Hostinger deployment is fully verified. See `V60.11-QA-REPORT.md` for checks actually executed and blocked checks.

- No database migration is introduced for V60.10 -> V60.11. Do not reset or re-seed your existing database.
- Keep a backup of your current project and database. Preserve the exact MongoDB database name, existing auth/encryption secrets and private environment settings. Do not expose secrets in chat, screenshots, commits or ZIPs.
- Preserve the existing tested `backend/package-lock.json` and `frontend/package-lock.json` when updating your working Git checkout. Dependency and override declarations are unchanged from V60.10. This source ZIP does not contain fabricated lockfiles: the supplied V60.10 archive did not contain them.
- The archive has ONE top-level folder: `SINGH-ACADEMY-V60.11-COMPLETE`. Open the folder containing `backend`, `frontend`, `scripts`, and `package.json` in VS Code.
- Update the existing Git repository later. Do not create a new Hostinger website, delete existing mailboxes or change production DNS during local testing.

## 1. Stop old development processes and verify Node

Stop the previous backend and frontend with Ctrl+C. Use Node 22.x, matching this project's `engines` declaration.

```powershell
node -v
npm -v
```

If Node is not 22.x, use your installed Node version manager or the Node 22 installer before testing. This guide does not assume a particular version manager is installed.

## 2. Set LOCAL environment values (do not replace your credentials)

Edit `frontend/.env.local` locally. These two entries must point to this local backend, not the Hostinger app:

```env
NEXT_PUBLIC_API_URL=/api
API_PROXY_TARGET=http://127.0.0.1:5000
```

In your existing local `backend/.env`, retain your real configuration and use these local origins:

```env
NODE_ENV=development
DEPLOYMENT_STAGE=development
PORT=5000
FRONTEND_URL=http://localhost:3000
FRONTEND_URLS=http://localhost:3000
PUBLIC_API_URL=/api
```

Keep `MONGODB_URI`, `AUTH_SECRET`, SMTP and Stripe TEST/PayPal SANDBOX credentials valid. Never leave `GENERATE_WITH_NPM_RUN_SETUP` as an actual auth secret. Reuse your existing stable secret rather than changing it on each update. No live payment credentials for these tests.

The retired admin MFA / signup-email verification gates stay retired. Password-reset email confirmation, password checks, cookie revocation, role separation and verified payments are retained.

These development settings are for localhost only. They must not be copied blindly to a publicly accessible Hostinger backend. V60.10's production upload-scanning / upload-disabled-review rules remain in place.

## 3. Install and verify — run one command at a time

Run from the project root. Stop on the FIRST error; keep the terminal output, not secrets.

```powershell
npm run install:all
npm --prefix backend run preflight
npm run verify
```

`install:all` runs `npm ci` when a package-lock exists; otherwise it runs `npm install` and creates the lockfile. Commit both resulting lockfiles after review. Do not delete them on every release, and do not run `npm audit fix --force` to suppress a failure.

`verify` includes controlled reliability checks, protected-asset checks, backend tests, the installed Sharp smoke test, sample certificate generation, TypeScript checking, a Next production build, source checking and production dependency audits. Full browser tests below are a separate gate.

You can also check the FULL dependency trees (including development tools):

```powershell
npm --prefix backend audit
npm --prefix frontend audit
```

Counts in the QA report apply to the saved run, not a future audit database. A newly reported advisory must be investigated, not ignored.

## 4. Run the real Next/React authentication-browser regression suite

Install this project's browser binary AFTER installing dependencies:

```powershell
Push-Location frontend
npx playwright install chromium
Pop-Location
npm run test:auth-browser
```

The browser command starts a controlled loopback API fixture on port 5109 and ACTUAL Next.js on port 3108. It exercises real middleware, React hydration, pages, proxy cookies, Back, explicit credential submission and logout. It does NOT connect to Atlas, send mail or make a real payment. Credentials in that fixture are synthetic, not administrator credentials.

It watches browser `pageerror` and hydration console messages. Cases include first guest load, server-unavailable/client-ready hydration, autofilled Back button without a login POST, login to /home or the requested route, logout from Events, refresh/Back and cross-tab logout.

Run the full existing UI suite as well:

```powershell
npm run test:ui
```

An unrelated global `playwright` binary is not a substitute for the project dev dependency. If `playwright test` is reported as unknown, confirm `npm --prefix frontend ls @playwright/test` after a successful `install:all`.

These real Next browser tests were ADDED but could not be executed in the packaging environment because project Next/React/Playwright dependencies could not be installed there. Do not interpret the controlled hook tests or header screenshots as proof that this gate passed.

## 5. Run your local application

Terminal 1, project root:

```powershell
npm run dev:backend
```

Keep it open. Check `http://127.0.0.1:5000/api/health`. Expected version: `60.11.0`.

Terminal 2, same project root:

```powershell
npm run dev:frontend
```

Keep it open. Open `http://localhost:3000`, then `http://localhost:3000/api/health`.

Terminal 3:

```powershell
npm run deploy:check -- --local --front http://localhost:3000 --api http://127.0.0.1:5000
```

Both backend and frontend build identity must be V60.11.0. The front `/api/health` forwards the BACKEND version; `api/app-build` independently identifies the FRONTEND build. Do not infer frontend version solely from a proxy health response.

If direct port 5000 works but 3000 `/api/health` fails, inspect the response error code and the frontend API proxy target. Restart Next after an environment change. A backend-proxy 503 is not proof of a missing course or an expired session.

## 6. Signed-in acceptance — do not clear old cookies before the first test

Use your existing browser first so legacy-cookie cleanup is exercised. Then repeat in a new private window.

| Test | Required result |
|---|---|
| Signed-out `/` | Marketing landing page remains public. |
| Guest About / Team / Courses / Events, by link or direct URL | Login opens with an encoded safe `next` destination. `?next=%2Fabout` is an intentional return address, not an error. |
| Login with no destination / destination `/` | `/home`, not the guest landing. |
| Login with `/events`, `/about`, `/checkout?...` | That safe requested page opens. |
| Valid previously signed-in student opens `/` | `/home`. This is an existing valid session, not a bypass. |
| Autofilled login form -> Back | `/`; NO login POST, no authenticated state. |
| Logout while on Events/About/learning | Button responds immediately; confirmed server logout then `/`. It must not remain at 'Opening sign in'. |
| Logout -> Back -> refresh -> menu click | No old identity or private content; credentials are required again. |
| Logout in another tab | Other protected tabs clear the old account; a NEW explicit login may intentionally restore authentication. |
| Failed logout because backend is offline | Local signed-out fence and an honest revocation warning persist. Restore backend and retry sign-out. Do not claim server revocation succeeded. |
| Valid session during normal navigation / temporary network error | No fabricated logout; retry message when needed. |
| Two distinct student accounts | Progress, answers, billing and certificates remain owner-scoped. |

If a browser/password manager offers automatic credential submission, disable that specific extension feature for acceptance testing. The application itself does not submit a login on Back or ordinary navigation.

## 7. Loading, videos and payments

- Header/footer links show navigation feedback immediately. A slow GET transition gets a safe Continue link, not an automatic mutation retry.
- Test the same recorded video in two lessons: each newly opened lesson begins at zero. The visible player prepares metadata/known providers behind the poster; offscreen players remain bounded/lazy. External providers, stream availability, network, codec and host bandwidth can still delay first frames.
- In Stripe TEST / PayPal SANDBOX, double-tap once and confirm there is one logical checkout key/order. Inspect both student My Billing and administrator course invoices.
- Simulate losing the CHECKOUT-CREATION response. The screen must check `/payments/checkout-status` with the SAME key, not silently create a new purchase. A new checkout becomes available only after the existing order is terminal, and still requires confirmation.
- After provider Back, the button must not remain permanently busy; any resumed request keeps the same key.
- Test actual provider confirmation/webhooks, membership access, invoices, receipts, cancellation and return flow. A local configuration PASS is not a payment proof.
- Do not buy again just because a confirmation page is slow. Check the existing checkout and My Billing first.

Configuration-only/local SMTP checks:

```powershell
npm run payments:check
npm --prefix backend run mail:verify
```

SMTP authentication does not prove inbox delivery. A real sandbox purchase using an allowlisted TEST student's account verifies the intended inbox. `info@singhacademy.com` is only a test recipient if that student's account uses that email; it is not a global replacement for students' addresses.

## 8. Judge local production-build performance separately

`next dev` compiles on demand. After `npm run verify` succeeds, stop the frontend dev server before running the already-built frontend with a loopback-only test allowance:

```powershell
$env:API_PROXY_ALLOW_LOCAL_TEST_ONLY='true'
npm run start:frontend
```

This flag in the existing proxy is accepted only when BOTH the actual request host and target are loopback; it is not a public deployment bypass. Keep the backend on 5000 running, test at localhost:3000, then stop the frontend and remove the temporary shell value:

```powershell
Remove-Item Env:API_PROXY_ALLOW_LOCAL_TEST_ONLY -ErrorAction SilentlyContinue
```

Do not set this flag in Hostinger. Measure real navigation/media/payment timings rather than assuming a fixed millisecond guarantee.
