# Singh Academy V60.12.0 — one local verification gate, then deployment acceptance

## Scope and non-destructive installation

This is a targeted update to the supplied V60.11.1 project: free-course start, safe payment retry/recovery, and reliable browser test infrastructure. The public layout, footer, certificate renderer/artwork and stored certificates are not redesigned. No database migration, reset or seed is introduced.

Use the complete ZIP OR the PATCH ZIP, not both. The complete ZIP contains one folder, `SINGH-ACADEMY-V60.12-COMPLETE`. Open the directory containing `backend`, `frontend`, `scripts` and `package.json` in VS Code. For the patch, copy its CONTENTS over that same project root; do not nest it under frontend.

Stop previous application/test terminals with Ctrl+C first. Back up the working project/database. Preserve private `.env` settings, the exact MongoDB database name, stable AUTH_SECRET, and your tested backend/frontend `package-lock.json` files. This source archive contains neither private credentials nor fabricated lockfiles. Dependency/override declarations are unchanged from V60.11.1. Installation uses the existing locks; without locks it resolves dependencies and creates them. Review and commit the resulting locks, not secrets.

## One command for all local checks

Use Node **22.x**, from the project root:

```powershell
node -v
node -p "require('./package.json').version"
npm run verify:release
```

The version must be **60.12.0**. `verify:release` runs, in order, and stops on the first failure:

1. Dependency installation using existing locks when supplied.
2. Backend configuration preflight.
3. Existing `verify`: controlled reliability tests, protected assets, backend tests, Sharp smoke, sample certificate generation, full TypeScript, ordinary Next production build, syntax/import checks and production dependency audits.
4. Full backend and frontend dependency audits, including development tools.
5. Project Playwright Chromium installation.
6. The **full actual Next/browser suite once**, including auth, free Start, certificate update and **17 synthetic payment cases** (41 total cases currently declared).
7. Payment configuration check, with no charge creation.
8. SMTP connection/authentication check, not inbox delivery.

A report is written to `qa/release-checks.json`. `not_run` means not tested, never passed. The full browser suite includes the authentication suite, so running `test:auth-browser` separately first is unnecessary. No failed assertion is skipped or given an increased expectation timeout in this update. Browser stack STARTUP has a 240-second allowance because it builds before the tests; individual test/expectation timeouts are retained.

The browser stack owns a fixed `.next-ui-tests` build, not your `.next`. It builds actual Next in production mode before executing tests, then uses `next start`; only the fixture build disables standalone packaging for that command. Normal production build still produces standalone output. It starts a controlled loopback API at 5109 and frontend at 3108, then cleans up its own processes. Do not manually open a second test stack or run commands concurrently. It refuses a second owner rather than killing arbitrary Node processes.

The new fixture never connects to Atlas, SMTP, Stripe or PayPal. Hosted provider addresses are intercepted by synthetic local browser pages. A fixture PASS is NOT proof of an actual provider settlement, webhook signature, Mongo transaction or email delivery.

Focused reruns after a specific failure, without repeating installation:

```powershell
npm run test:ui
# Only the new payment browser cases, when diagnosing payments:
npm run test:payments-browser
```

Next manifest errors such as `Unexpected end of JSON input` are not ignored: they are recorded in `frontend/qa/ui-runtime-errors.log` and fail the browser command even if page assertions pass.

### Actual sandbox payments and email — separate from the synthetic suite

Use your configured Stripe test account and PayPal sandbox application. Do not use real/live money for debugging. Use dedicated students/products, so an existing membership does not hide a paid-course checkout.

Test an individual course and a membership through **each** provider. Record the provider order reference and local invoice, not card data or secrets. Confirm one paid invoice, receipt, correct student's grant/term and the corresponding administrator record. Test mobile return/Back, cancellation, a slow confirmation and replay/refresh without duplicate grants or notifications. Do not purchase again solely because a response is slow.

An unresolved checkout now retains owner/product/provider/option/key in that tab's session storage (not card data, price or a paid flag). It disables switching to a different provider/option until the server confirms that checkout is closed; a new checkout then requires an explicit click. A browser cancel URL alone is not proof of a failed/unpaid transaction. If storage is blocked, recovery is limited to the current mounted page; cross-device/global exactly-once purchase is not claimed.

After both public webhook URLs are deployed and credentials match the intended environment, the read-only remote configuration check is:

```powershell
npm --prefix backend run payments:check -- --remote --strict-webhooks
```

This checks provider credentials/registration, not delivery. A real sandbox checkout and provider delivery logs are still needed. Local browser return tests do not prove that a public webhook reached the local backend. Stripe CLI forwarding or a correctly configured public review backend is needed when checking actual delivery; do not replace webhook secrets with unrelated environment values.

For actual sandbox emails, opt in only the test student's exact email with existing `SEND_SANDBOX_EMAILS` / `SANDBOX_EMAIL_ALLOWLIST`. `info@singhacademy.com` is a test recipient only if the purchasing student's email is that address, never a global replacement for other students. SMTP authentication alone does not prove inbox delivery. Confirm the actual message in the intended inbox and the delivery/notification record. No fixture sends a real email.
